# Backfill companion — `rule_checks.normalized_value`

## Що і чому

`rule_checks` отримує NOT NULL колонку `normalized_value` (ADR-0001: нормалізоване
значення зберігається окремо від сирого `source_value`, щоб diff-детектор і подальший
аудит могли перевірити саме крок нормалізації, а не лише кінцевий висновок). Виявлено
post-hoc після greenfield-проходу генерації моделі.

## Дизайн бекфілу

- **Ідемпотентний.** `WHERE normalized_value IS NULL` — повторний запуск чіпає лише
  рядки, які попередній прогін не встиг обробити.
- **Курсор.** Реальний прогін (не сирий SQL із staged-міграції) — batched по `id` через
  UUID-курсор, розмір батчу 500 рядків, пауза між батчами — той самий патерн, що
  `fetch-zus-benchmark.mjs` мав би використовувати для rate-limit (§4 стовп 2 SAD), але
  тут — навантаження на власну БД, не на зовнішнє джерело.
- **Raw SQL у staged-файлі — заглушка.** `UPDATE ... SET normalized_value = source_value`
  копіює сире значення як є; справжня нормалізація (парсинг числа з тексту, ADR-0001) —
  функція `normalize.mjs`, викликається з батч-скрипта застосунку, не з SQL-міграції.

## ETA і resumability

- Обсяг: rows-per-cycle × кількість минулих циклів. При типовому обсязі (9-26 записів на
  цикл, allowlist-скоуп цієї фічі — §11 ризик «34.6% покриття») — секунди, не години;
  батчування описано на випадок майбутнього розширення allowlist.
- **Resumable.** Перерваний прогін просто перезапускається — `WHERE normalized_value IS NULL`
  підбирає рівно те, що лишилось необробленим, без ручного трекінгу прогресу.

## Rollback

Дані, записані бекфілом, назад не «розбекфілюються» (нема сенсу null-ити реальні
значення). Відкат цієї фази — це відкат expand-фази (`20260807130100_*.down.sql`),
яка дропає колонку разом із даними.
