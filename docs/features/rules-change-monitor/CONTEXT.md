## Glossary

- Хранитель матриці — роль засновника як відповідального за точність `rules.2026.json`; той самий Mike, у ролі, окремій від «Дослідник ринку» (`tg-assistant`) чи майбутнього «Платний підписник» (v2, поза межами v1-шару). NOT «платний підписник» (v2-роль, отримує персональні алерти — не існує в цій фічі); NOT «анонімний користувач навігатора» (безкоштовний шар — мовчазний бенефіціар точності, не актор жодного US тут).
- дрейф — застарілий `verified_at` запису в `rules.2026.json` без підтвердження, що джерело досі актуальне. NOT «зміна правила» (дрейф — це невідомість/час без перевірки, а не зафіксований факт, що щось реально змінилось).
- звірка — повторний цикл перевірки вже внесеного в `rules.2026.json` запису: чи розійшлось значення в джерелі з тим, що записано. NOT «первісна верифікація» (одноразова перевірка нового правила при першому додаванні в matrix через `/scaffold-rule`, а не повторний моніторинг вже внесеного).
- зміна правила — подія: офіційне джерело (zus.pl, podatki.gov.pl, zakon.rada.gov.ua) опублікувало нове значення чи текст для запису, який вже є в `rules.2026.json`. NOT «оновлення застосунку» (deploy нової версії коду/UI, не повʼязаний зі зміною цифри в джерелі).
- сповіщення — повідомлення користувачу, персоналізоване під його сценарій (форма, резидентство): саме ЦЯ зміна правила стосується саме його профілю. NOT «розсилка» (масове повідомлення всім підписникам однаково, без фільтрування під профіль).
- `rule_check` — окремий запис результату звірки одного `rule_id` у межах одного циклу (`data-model.md` → `rule_checks`: `state`, `source_value`, `matrix_value`, `diff_percent`, `checked_at`). NOT «`rule`» (запис самої матриці `rules.2026.json` — статичне визначення норми; `rule_check` — динамічний результат перевірки цього запису в конкретному циклі, ефемерний факт часу, а не сама норма).
- veto-запис — запис у `veto_entries` про свідомо скасовану/ветовану цифру (напр. ставка реформи zdrowotnej), яку джерело може помилково повернути знову (AC-10, Потік 3). NOT «deprecated» (застаріла норма, яку продукт більше не використовує, але яка ніколи не була дійсною цифрою джерела, що повторно з'явилась — veto специфічно про повторну появу вже скасованого значення, не про застарілість самого запису).
- цикл (`cycle_run`) — один щомісячний прогін звірки всіх записів allowlist-скоупу проти джерел, ідентифікований `month` (`YYYY-MM`, UNIQUE у `cycle_runs`). NOT «одноразовий виклик скрипта» (ручний ad-hoc прогін поза розкладом технічно можливий, але семантика того, чи створює він новий `cycle_run`, — відкрите питання PRD §8; поточна модель — один цикл прив'язаний до календарного місяця, не до окремого процесу).
- allowlist (автозвірки) — власний список доменів у `allowlist.mjs` (ADR-0003), для яких rules-change-monitor підтверджено вміє скриптовано читати значення (`zus.pl`, `podatki.gov.pl`). NOT «firewall allowlist» (`.devcontainer/init-firewall.sh` + `.claude/settings.json` — мережевий дозвіл на домен; ширший список, не кожен домен із нього має скриптовану підтримку — ADR-0003 прямо розрізняє два поняття).
- стан звірки — одне з 7 фіксованих значень `rule_checks.state` (AC-03: «збігається» / «розбіжність» / «косметична відмінність» / «не вдалось перевірити» / «поза автозвіркою» / «потребує підтвердження» / «ще не верифіковано»). NOT «зміна правила» (зміна правила — подія в реальному світі на джерелі; стан звірки — категоризація конкретного `rule_check` в конкретному циклі, яка може бути «розбіжність» і без реальної зміни джерела — напр. якщо матриця раніше мала помилку).

## Invariants

- Кожен `rule_check` завжди належить рівно одному `cycle_run` (`cycle_id` NOT NULL, FK) — жоден результат звірки не існує поза циклом.
- `veto_entries` ніколи не видаляється, лише додається (PRD §8: «поповнюється вручну при кожному новому інциденті») — список лише росте.
- Запис `rules.2026.json` поза allowlist-скоупом завжди отримує стан «поза автозвіркою» і система ніколи не звертається до його джерела автоматично (AC-02) — без винятків у коді.
- `rule_checks` рядок ніколи не редагується заднім числом (немає `updated_at`, `data-model.md`) — звіт минулого циклу завжди показує те, що зафіксовано в момент звірки (AC-06 закривається immutable-by-construction, не окремою логікою).
- Запис зі станом «не вдалось перевірити» завжди повторюється в наступному циклі — ніколи не пропускається мовчки назавжди (AC-09, Потік 2).

## Sentinel errors

<!-- Немає JSON error-реєстру (`module.error_name`) — фіча без публічного API/events-межі
процесу в цьому сенсі (той самий висновок, що contract-forge: error envelope лише там, де
є межа процесу). Натомість типові причини недоступності джерела — текстове доменне поле
`rule_checks.failure_reason` (`data-model.md`), не структуровані коди. -->

- `timeout` — джерело не відповіло у відведений час на мережевому рівні.
- `waf_block` — джерело відповіло, але через WAF (Incapsula/Akamai — `302` на себе, далі
  `403`, той самий патерн, що задокументований для `isap.sejm.gov.pl`/`tax.gov.ua` у
  [environment-limits.md](../../../.claude/rules/environment-limits.md)), не справжнім
  контентом.
- `challenge_page` — джерело віддало HTML challenge-сторінку замість очікуваного значення:
  проміжний стан між «недоступно» й «success» — контент є, але не той, що очікується.

Усі три — значення `rule_checks.failure_reason` (Потік 2, AC-08), не окремий
error-registry-файл: домен-поле в тому самому записі, не JSON-каталог кодів.

## Org-filter invariant

`N/A: немає org-межі, соло-локальний інструмент.` rules-change-monitor — приватний
скрипт одного власника матриці (Хранитель, той самий Mike — глосарій вище), без
multi-tenant поділу: продукт client-only, без бекенду/БД, що обслуговував би кількох
Хранителів (`docs/architecture-map.md` §Сховища даних: «БД — Немає»). Авторизаційна
межа тут — не org, а allowlist-скоуп джерел (AC-02, вище) — інша вісь розрізнення.

## Out of scope

- Персоналізовані push-сповіщення платним підписникам (повний v2-шар доставки) — PRD §3,
  відкладено до стабілізації v1 хоча б один сезон.
- Автоматичний моніторинг `isap.sejm.gov.pl` і `tax.gov.ua` — обидва за WAF, який відхиляє
  автоматизовані запити незалежно від середовища (`environment-limits.md`); скриптованого
  шляху не знайдено.
- Будь-яка порада, що робити зі зміною правила — фіча лише позначає, що значення
  змінилось, і ніколи не радить дію (`product-safety.md`).
- Автоматична правка `rules.2026.json` (значень `params` чи `verified_at`) — звірка лише
  позначає стан у звіті; оновлення матриці лишається ручною дією через `/scaffold-rule`.
