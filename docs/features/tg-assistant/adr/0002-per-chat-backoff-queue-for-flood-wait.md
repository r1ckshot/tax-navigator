# 0002 — Per-chat exponential-backoff queue keyed on Telegram's FLOOD_WAIT_X

- **Status:** Accepted
- **Date:** 2026-08-06
- **Deciders:** Mike + Claude (architecture-design, Socratic walk)

## Context

Прямий MTProto-клієнт (ADR-0001) сам відповідає за обмеження частоти
запитів — MCP-сервер більше цього не ховає. `research/tg-mining/01-SETUP.md:35`
вже документує реальний інцидент ручних раундів збору: Telegram віддає
`FLOOD_WAIT_X` при частих запитах, і це вже названо технічним обмежувачем
у `sad.md` §2. NFR вимагає ≥10 чатів за прогін без переривання (PRD §6) —
без явної стратегії один `FLOOD_WAIT` на одному чаті ризикує зупинити весь
тижневий цикл.

## Decision drivers

- Технічний обмежувач із §2: `FLOOD_WAIT_X` (`research/tg-mining/01-SETUP.md:35`).
- NFR «≥10 чатів за прогін без переривання через rate limit» (PRD §6).
- PRD §6.1 abuse case: «пауза й експоненційний відступ при обмеженні
  частоти, а не тихий обрив».
- AC-08: система явно називає чати, які не вдалося прочитати, — не
  правдоподібний нуль.

## Considered options

1. **Черга по чатах з експоненційним відступом, що читає X із помилки** — при
   `FLOOD_WAIT_X` призупиняє лише цей чат на X секунд, інші чати продовжують.
2. **Фіксована затримка між усіма запитами** — однакова пауза завжди,
   незалежно від реальної помилки Telegram.
3. **Без обмежень до першої помилки, потім обрив прогону** — найпростіше,
   але суперечить AC-08 і §6.1 напряму.

## Decision outcome

**Обрано:** Опція 1. Читання реального `X` з помилки Telegram — не вгадана
константа — і призупинення саме проблемного чату (не всього прогону)
напряму задовольняє і NFR throughput, і AC-08 «явно назвати, що саме не
прочиталось», замість ховати частковий збій за спільною паузою.

## Consequences

**Positive**
- Один зациклений чат не зупиняє прогін решти ≥10 (NFR §6).
- AC-08 отримує точну причину («цей чат — `FLOOD_WAIT_180`»), не узагальнене «збій».

**Negative**
- Черга по чатах складніша за глобальну паузу — окремий стан на чат
  (наступний дозволений момент запиту), а не один таймер.
- Гірший випадок (усі чати одночасно у `FLOOD_WAIT`) все одно наближається
  до бюджету ≤30 хв — потребує окремого сценарію в §10.

**Neutral**
- Той самий механізм відступу переюзається backfill-режимом AC-10 (довший
  бюджет ≤2 год), окремого рішення для нього не потрібно.
