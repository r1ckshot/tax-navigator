# CAPSTONE_LOG — M5, вимірювання F1 vs F2

Лог експерименту capstone Module 5: та сама форма наскрізного зрізу робиться двічі —
**F1 руками** (плагін вимкнений) і **F2 через плагін** — щоб побачити, що саме варте
автоматизації і чи справді плагін щось прискорює.

Завдання називає цей файл то `LOG.md`, то `CAPSTONE_LOG.md`. Тут одна назва і один файл:
дві копії неминуче розійшлись би (CLAUDE.md, «ніколи в двох місцях одночасно»).

**Правило дописування:** після кожного коміту в `feat/f1-*` або `feat/f2-*` — рядок у
відповідній таблиці цього файлу (timestamp, крок, метрика). Записується фактом, не
підсумком: якщо промпт довелось повторити тричі — так і пишеться.

**Що таке «вільний промпт»:** будь-яке звернення до агента, написане текстом. Виклик
команди плагіна (`/scaffold-scenario …`) рахується за **один** промпт, скільки б кроків
він усередині не зробив.

---

## Зріз, який повторюється двічі

| Шар | Що з'являється |
|---|---|
| rules | блок правил `<slug>.*` у `app/lib/rules/rules.2026.json` із `source_url` + `verified_at` |
| calc | `app/lib/calc/scenarios/<slug>.ts`, `ScenarioId` у `types.ts`, реєстрація в `scenarios/index.ts` |
| adapters | i18n-ключі в `app/lib/i18n/uk.ts` |
| presentation | рядок у порівнянні (`ComparisonTable`) і картка (`ScenarioCard`) |
| tests | гілки логіки, еталон у `benchmark.test.ts` (виведений вручну), рядок у `flow.test.tsx` |
| docs | EVIDENCE (верифікація джерел), SPEC (кількість сценаріїв) |

## Гілки і PR

F1 і F2 навмисно мають однакову форму — інакше порівняння читається як порівняння
різних речей. Плагін лежить окремо від обох: він мусить існувати **до** F2, і в
спільному PR ця хронологія була б невидима.

| Гілка | Що всередині | PR |
|---|---|---|
| `feat/f1-umowa-zlecenie` | F1 руками: 5 комітів | PR #1, змерджено в `master` через rebase |
| `feat/m5-capstone-plugin` | Етап 2 — хук, скіли, toolkit 1.0.0: 4 коміти | PR #2, змерджено в `master` через rebase |
| `feat/f2-dzialalnosc-nierejestrowana` | F2 через плагін: джерела → код+тести → документи | [PR #3](https://github.com/r1ckshot/tax-navigator/pull/3), база — `master` |

Усі три PR — англійською, як і коміти.

Один коміт у PR #3 не про сценарій: `chore(claude): wire layer-boundary hook into
settings`. Він лишився боргом Етапу 2 — PR #2 уже був змерджений, коли виявилось,
що сам wiring не закомічений, тобто у свіжому клоні хука не було. Він їде разом
із F2 свідомо: саме він робить хук живим, а спрацювання хука під час F2 — предмет
виміру. Ховати цю послідовність в окремому PR означало б причесати історію.

**Свідоме відхилення від рубрики.** Завдання просить код у теках `feature-1/` і
`feature-2/` — це структура навчального scaffold з M4.12. Тут реальний продукт:
обидві фічі — сценарії в `app/lib/calc/scenarios/`, і покласти їх у `feature-N/`
означало б зламати межі шарів, які цей самий capstone і стереже хуком
`layer-boundary`. Межа F1/F2 проходить по гілках, PR і комітах — вона не менш
явна, просто не в назві теки.
