# env-scout — MEMORY

Симптом → діагноз → обхід, для машинної звірки на старті кожної сесії.
Людський журнал — `docs/JOURNAL.md`. Чинний стан для всіх сесій —
`.claude/rules/environment-limits.md` (редагує лише Mike).

## Auto-mode класифікатор блокує й Edit, і довільний (не allow/ask-листований) Bash
- **Симптом:** `Edit` по `.claude/hooks/block-env-writes.mjs` → `Permission for this action was denied by the Claude Code auto mode classifier. Reason: Blocked by classifier.` Приблизно за хвилину той самий вердикт отримав `Bash(strings <бінарник claude>)`, хоча два попередні виклики `strings` хвилиною раніше пройшли зелено. `permissions` у `.claude/settings.json` між викликами не мінявся.
- **Насправді:** той самий недетермінований auto-mode класифікатор, що вже описаний в `environment-limits.md` (рядок «Класифікатор auto-режиму проти `permissions`») на прикладі `gh pr merge` (в `ask`) і `npm run verify` (в `allow`) — але тут показано ширше: він так само переоцінює `Edit` і Bash-команди, яких у `allow`/`ask`/`deny` взагалі немає (і `Edit`, і `strings` там не згадуються, обидва йдуть під `defaultMode: acceptEdits` / без явного правила). Тобто межа проходить не по «командах з правилом», а по auto-режиму як такому.
- **Замір:** 2026-08-25, сесія env-scout — `Edit(.claude/hooks/block-env-writes.mjs)` denied; ~1 хв по тому `Bash(strings ...)` denied, при цьому 2 попередні `Bash(strings ...)` в тій самій хвилині — success; diff `.claude/settings.json` за цей проміжок відсутній.
- **Обхід:** той самий, що вже в `environment-limits.md` — повторити операцію (сам факт відмови не означає зламане правило чи зіпсований файл); при повторній відмові — Shift+Tab на acceptEdits або почекати.
- **Хибний слід:** можна було подумати, що `.claude/hooks/**` навмисно захищений від редагування окремим правилом — у `settings.json` такого правила немає (перевірено читанням файлу), це чистий шум класифікатора, а не політика.

## Реєстрація нових .claude/agents/*.md — не «раз на старті сесії», а недетерміновано
- **Симптом:** три нові файли (`diff-reviewer.md`, `env-scout.md`, `rules-auditor.md`), створені сьогодні о 13:26–13:37, стали доступні для спавну **в тій самій сесії**, що їх створила, за кілька хвилин — ця сесія env-scout сама є доказом (файл `env-scout.md`, `13:28`, уже виконується).
- **Насправді:** чинний запис `environment-limits.md` від 2026-08-25 («Нові `.claude/agents/*.md`…») діагностує поведінку як «реєстр читається один раз на старті, як `~/.claude/settings.json`» — на прикладі `ro-reviewer.md`, який того ж дня, але в **попередній** сесії, не зареєструвався за 5 спроб/~25 хв і зʼявився лише в наступній. Сьогоднішнє спостереження (три інші файли, той самий часовий проміжок) цей діагноз **спростовує**: якби реєстр читався рівно один раз при старті сесії, жоден новий файл не міг би стати доступним усередині тієї ж сесії — а тут стало, і швидко. Правильніша модель — недетермінована затримка реєстрації (іноді хвилини в тій самій сесії, іноді не встигає взагалі і треба нова сесія), а не фіксоване «раз на старт».
- **Замір:** 2026-08-25, `ls -la .claude/agents/` → `diff-reviewer.md` 13:26, `rules-auditor.md` 13:27, `env-scout.md` 13:28; усі три успішно заспавнились у сесії створення протягом кількох хвилин. `ro-reviewer.md` у тому ж лістингу має mtime 13:37, але це **не** час його створення — файл створено в попередній сесії того ж дня, а 13:37 це правка `model: opus` у цій сесії. Порівняння коректне на рівні «інша сесія, той самий день, протилежний результат», не на рівні хвилин.
- **Обхід:** не відкладати спробу спавну на «наступну сесію» за замовчуванням — пробувати одразу; якщо кілька спроб поспіль у тій самій сесії не спрацювали (як з `ro-reviewer`), тоді вважати недоступним до нової сесії — цей fallback лишається робочим, просто не єдиним сценарієм.
- **Хибний слід:** діагноз «реєстр агентів читається один раз на старті сесії, як `~/.claude/settings.json`» — сам цей запис від 2026-08-25 в `environment-limits.md`, і саме сьогоднішнє (пізніше того ж дня) спостереження його й спростовує.
