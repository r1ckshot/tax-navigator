## Чому «зависали» Next і jsdom (розібрано 2026-07-24)

**Це була не блокуюча операція, а повільна файлова система.** Попередня версія
цього файлу звинувачувала seccomp — **діагноз був хибний**, лишаю запис як
застереження проти висновків з надто коротких таймаутів.

Вимір `stat`+`read` на 400 файлах:

| Шлях | stat | read |
|---|---|---|
| `/workspace` | 9.63 мс/файл | 10.43 мс/файл |
| `/tmp` (overlay контейнера) | 0.01 мс | 0.02 мс |
| `/usr/local/lib/node_modules` | 0.02 мс | 0.13 мс |

`/proc/mounts` показує причину: `C:\ /workspace 9p … aname=drvfs`. Тека проєкту
живе на диску Windows і ходить у контейнер через 9p — кожен файловий доступ
приблизно в 500 разів дорожчий.

Арифметика сходиться: `require("jsdom")` тягне **3615 модулів × ~22 мс = 80.6 с**
(доведено інструментованим `Module._load`, який дорахував до кінця). Дефолтний
таймаут воркера vitest — 60 с, тому jsdom не «не стартує», а не встигає. `next dev`
з тієї ж причини виглядає мертвим.

**Контрольний прогін на ФС контейнера** (копія проєкту в `/tmp`, `npm ci` — 18 с):

| Команда | На `/workspace` | На `/tmp` |
|---|---|---|
| `next dev` | нескінченно | **Ready за 2.3 с**, `/` і `/questionnaire` → 200 |
| `npm run test:ui` | таймаут воркера | **10 тестів за 5.8 с** |

Раніше «виключені» гіпотези (sandbox, породження процесів, IPC, мережа, `.next`,
нативний SWC, Turbopack) виключені правильно — просто жодна з них і не була
причиною. Пункт «той самий застосунок висне і в `/tmp`» був хибним виміром:
застосунок лежав у `/tmp`, а `node_modules` резолвився з `/workspace`.

**Обране й застосоване рішення (2026-07-24): том для `node_modules`.**

`devcontainer.json` монтує named-volume `tax-navigator-node-modules` на
`/workspace/node_modules` (нативний ext4), `Dockerfile` готує теку від root, щоб
свіжий том належав `node`, `postCreateCommand: npm ci` його наповнює,
`WATCHPACK_POLLING=true` рятує HMR (inotify через 9p не працює). Вихідники
лишаються bind-ом на `C:\` — їх мало, 9p на них терпимий.

Заміри після Rebuild Container: `test:ui` 60 с (холодний кеш) → **12 с** (теплий,
кеш vite теж на томі); `next dev` **Ready 6.4 с**, сторінки → 200. Перший прогін
будь-чого повільний через холодний кеш — це разово, не баг.

**Доповнення 2026-07-28: справжня причина краху `Cannot find module './NNN.js'`.**
Спершу списали на 9p і винесли `.next` у named-volume `tax-navigator-next` — том
корисний (ext4 замість 9p пришвидшує dev-кеш), але **краху він не лікував**.
Реальна причина: `next build` і `next dev` ділили одну теку `.next`. Клод багато
разів ганяв `npm run build` для перевірки в тому ж контейнері, де Mike потім
відкривав `npm run dev` — dev спотикався об артефакти продакшн-збірки
(`server/pages/_document.js`, `webpack-runtime.js` з посиланнями на неіснуючі в dev
чанки). Діагностика: `ls .next/BUILD_ID` — якщо є, у теці лежить білд, і dev
зламається.

Виправлення:
- **`next.config.mjs`: `distDir: process.env.NEXT_DIST_DIR || '.next'`** — щоб білд
  можна було спрямувати в окрему теку. Vercel без цього env → дефолт `.next`.
- **Політика: Клод не запускає `next build` у контейнері Mike.** Перевірка —
  `tsc --noEmit` + `npm test` + `npm run test:ui` (жоден не чіпає `.next`). Виявилось,
  що навіть `NEXT_DIST_DIR=.next-verify` частково протікає в `.next`, тож надійніше
  просто не білдити тут; продакшн-збірку валідує Vercel на деплої.
- Якщо `.next` уже засмічений білдом — `find .next -mindepth 1 -delete`, тоді `dev`.
  Перевірено 2026-07-28: після чистки `next dev` Ready 2.7 с, `/` і `/questionnaire`
  → 200 без module-error.

Розглянутий і відкинутий варіант — перенести весь репо на ext4 WSL2: чистіше в
теорії, але щоразу впиралось у reattach контейнера до старої `C:\`-копії, і
коштувало б втрати редагування з Windows. Том дає те саме прискорення без цього.
Якщо колись 9p на вихідниках почне муляти (важкі git-операції) — тоді переїзд у
WSL, але це вже комфорт, не блокер.
