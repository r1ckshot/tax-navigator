# Skill: architecture-design (стадії 04-05 — SAD + ADR, ворота)

12 секцій arc42 не пишуться підряд одним чорновиком — кожна проходить Socratic
walk і комітиться окремо, щоб дрейф між рішеннями ловився в дифі, а не через
місяць у коді. ADR — не на кожне рішення, а лише на те, що боляче перекроювати
(«масштаб удару» — 2 з 3 критеріїв нижче).

## Що на виході

`docs/features/<slug>/sad.md` — 12 секцій, C4 Context (Mermaid) inline у §3, C4
Container (Mermaid) inline у §5, frontmatter `target_surfaces: [...]` заповнюється
в §4. Плюс `docs/features/<slug>/adr/NNNN-<title>.md` (формат MADR, `Status:
Accepted`) — по одному файлу на кожне рішення, що спрацювало на gate. Шаблони:
[templates/sad-template.md](templates/sad-template.md),
[templates/adr-template.md](templates/adr-template.md). Синтаксис C4/Mermaid —
[references/c4-mermaid-syntax.md](references/c4-mermaid-syntax.md).

## Депт-діал (глибина)

Один регулятор на прогін: **easy** (скіл сам вирішує зворотні дрібниці,
питає лише незворотні/високого масштабу удару рішення, веде список припущень
на підтвердження одним пакетом) / **medium** (дефолт — питає кожне реальне
рішення) / **hard** (кожне рішення + trade-off на передньому плані, кожна
Mermaid-діаграма підтверджується прозою). Питати на кроці 1 через
`AskUserQuestion`, `medium` — рекомендована опція за замовчуванням. Blast-radius
gate і правило owner+due для відкритих питань — підлога, діє на будь-якому
рівні.

## Target-surface — перше рішення §4

Що саме будуємо: multiSelect над `backend-service` / `web-frontend` /
`mobile-app` / `desktop-app` / `cli` / `worker` / `library-sdk`, з PRD §1 «для
кого» + §4 ролей (PRD сам поверхню не називає). Записується у frontmatter
`target_surfaces: [...]` — читає (не передеривовує) кожна наступна стадія.
Гейтить §5: один C4 `Container` на кожну оголошену поверхню. Більше однієї
поверхні — майже завжди ADR (мультимодульно + незворотньо). На кожну **UI**-
поверхню (`web-frontend`/`mobile-app`/`desktop-app`) — окреме follow-on
рішення UI-архітектури (web → SSR/SPA/hybrid; mobile → native/cross-platform),
теж під gate; UI переюзає наявну дизайн-систему з `architecture-map.md`
§Фронтенд, не винаходить заново.

## 4 дії з рішенням (4-state machine, як в write-prd)

- **Прийняти** — лишити дослівно. Без запису в edits-log (baseline). Прогнати
  blast-radius gate.
- **Виправити** — нове формулювання одним заходом, скіл регенерує і питає ще
  раз (один раунд, друга відповідь фінальна). Лог `action: "edit"`.
- **Винести у відкрите питання** — рішення йде з секції, рядок додається у §11
  з owner+due (`Resolve before <дата/стадія>`). Обидва поля обовʼязкові —
  без одного з них downgrade у Викинути з попередженням. Gate не запускається.
- **Викинути** — обовʼязкове рішення (напр. межа модуля §5) → переформулювати
  опції, спитати ще раз; другий Drop → ескалація у Відкрите питання (owner =
  Architect, due = «до наступного проходу»). Опціональне — просто прибрати.

Edits-log: `{decision_id, action, before, after, user_reason}` на кожну
Виправити/Викинути/Відкрите-питання дію (Прийняти — не логується, це базова
лінія). Це єдиний сигнал, який критик використовує на кроці 7.

## Blast-radius gate («масштаб удару») — коли рішення стає ADR

Три критерії на кожне **Прийняте** рішення:

1. **Незворотнє** — переробка через 3 місяці зайняла б ≥3 днів? (вибір
   сховища, sync/async звʼязок модулів, ID-стратегія, модель авторизації)
2. **Мультимодульно** — контракт бачать ≥2 модулі? (event-схема між
   модулями, спільний неймспейс кодів помилок, конвенція пагінації)
3. **Є чесна альтернатива** — читач через півроку спитає «а чому не X»,
   де X не виключений обмеженням стеку (без соломʼяних опцій)?

**2 з 3 → ADR.** 1 з 3 — межовий випадок, питати явно (крім §4, де поріг
нижчий — стратегічні рішення за визначенням широкі). 0 → лишається inline у
`sad.md`. Очікувана кількість ADR за розміром: XS/S → 2-4, **M → 5-12**, L/XL
→ 10-15.

**Спавн ADR:** NNNN = `ls adr/*.md | wc -l` + 1 (4 цифри) → kebab-case
заголовок **рішення, не проблеми** (`0003-sliding-window-with-redis.md` ✓,
`0003-rate-limiting.md` ✗) → копія
[templates/adr-template.md](templates/adr-template.md) → `Status: Accepted`,
Context/Decision drivers/Considered options (усі, включно з відкинутими,
без соломʼяних)/Decision outcome/Consequences (Positive+Negative+Neutral
чесно)/Links (PRD, `sad.md §N`, сусідній ADR якщо разом — один договір) →
рядок у §9 → **той самий коміт секції**, окремого коміту на ADR немає.

## Критик (крок 7) + backstop-скани

Dispatch `sad-critic` (`.claude/agents/sad-critic.md`, read-only, чистий
контекст — не бачив Socratic-діалогу) з інлайном: повний текст щойно
записаного `sad.md`, edits-log, ADR-spawns log, шляхи до `PRD.md`,
`CONTEXT.md`, `adr/` (сам агент їх читає — без переказу). Шукає 6 класів:
F1 дрейф стратегії (§4 vs §6/§10) · F2 розповзання розміру (M → L) · F3
відкладене-vs-PRD-вектор (drop/OQ зачепив те, що PRD §6/§7/§13 назвав
критичним) · F4 тихі правки (текст ≠ `after` з логу) · F5 структурні дірки
(порожні секції без N/A, Mermaid-заглушки, сироти §9, §11-рядки без
owner+due) · F6 протиріччя (число в §10 не з PRD NFR, соломʼяна альтернатива
в ADR, §2 суперечить конвенціям репо без Override). Вивід — `≤7` знахідок,
кожна з цитатою, або `NO_CONTESTED_DECISIONS`. `CRITIC_BLOCKED: <причина>` →
СТОП, не писати фінальний коміт мовчки.

Кожну знахідку — окремим `AskUserQuestion`: **Прийняти правку як є** /
**Прийняти з іншим формулюванням** / **Override з обґрунтуванням** (останнє
дописує рядок у §1 ¶4 «Decision override», щоб наступні стадії бачили
свідомий вибір).

Потім три структурні скани (незалежно від критика):
- **Mermaid** — кожен блок §3/§6/§9 сад.md за
  [references/c4-mermaid-syntax.md](references/c4-mermaid-syntax.md):
  парні огорожі, розпізнаний перший токен, кожен елемент оголошено до `Rel`,
  що на нього посилається, без `Container_Bondary`, без залишків
  `<placeholder>`. `mmdc`/`node_modules/mermaid` в цьому контейнері нема —
  працює структурний лінт, не справжній парсер (як у `map-architecture`). Не
  парситься після 3 спроб — не комітити, показати блок і помилку Mike.
- **Формат назв ADR** — `NNNN-kebab-case.md`, заголовок-рішення (не
  проблема), `Status: Accepted`.
- **Сироти §9** — кожен файл у `adr/` має рядок у §9 і навпаки.

## Анти-патерни

- **ADR на кожне рішення** — вбиває жанр; лише те, що спрацювало на gate.
- **Пропустити критика крок 7** — саме він ловить дрейф між секціями, який
  Socratic walk по секції фізично не бачить (не повертається назад).
- **Один коміт на весь прохід замість по секції** — губить трасованість і
  можливість резюмувати перерваний прогін.
- **Соломʼяна альтернатива в ADR** (варіант, вже виключений обмеженням
  стеку) — розводнює жанр, ловиться критиком F6.
- **ADR зі `Status: Proposed`** — цей скіл синхронний (рішення приймається
  з Mike зараз), статус одразу `Accepted`.
- **Повернутись до записаної секції** — дрейф між секціями ловить лише
  критик крок 7, не повторний walk.
