# Прохід безпеки під загрози tax-navigator

Це **кастомізована копія** вбудованого `/security-review`. Вбудований лишається
доступним і корисним — його ганяємо на тому, де є межа процесу (MCP-сервер
`mcp/evidence-guard/`, вебхук, worker-скрипти `research/`). Цей скіл — для
`app/**`, де generic-версія структурно сліпа.

## Чому копія, а не вбудована команда

Вбудований прохід шукає SQL/command-інʼєкції, секрети, authz-обхід, XSS, PII.
У продукті немає **жодного** з цих класів: розрахунок детермінований і
клієнтський, бекенду нема, персональних даних нема, сирі доходи не зберігаються
(`product-safety.md`). Більше того, його ж власні false-positive-precedents
прямо кажуть, що клієнтський TS без перевірок прав — не вразливість. Прогін
generic-версії на реальному діфі `app/lib/calc/` дав нуль знахідок при трьох
навмисних порушеннях у дереві (заміряно 2026-08-22, урок 9.5).

Наш ризик інший і в одну фразу: **продукт продає довіру до чисел і не має права
радити.** Зламана довіра не має відкату — користувач ухвалив рішення про гроші.

## Що перевіряти (три P0, кожен уже описаний правилом репо)

Знахідка без прив'язки до одного з цих правил — не P0. Не вигадувати четвертий
клас на ходу: розширення threat-model — окреме рішення, не імпровізація рев'юера.

### P0-1. Цифра, яку побачить користувач, без `source_url` + `verified_at`

Правило: [`evidence-numbers.md`](../../rules/evidence-numbers.md).

Ловити:
- числовий літерал у `app/lib/calc/**`, що потрапляє в результат (ставка, ліміт,
  поріг, база, множник). Легальні винятки — суто арифметичні константи
  (`/ 12`, `* 100`, `round2`), не податкові величини;
- нове правило в `app/lib/rules/rules.2026.json` без пари `source_url` +
  `verified_at`;
- **змінене число при незміненому `verified_at`** — мовчазна правка величини
  заборонена окремим рядком правила;
- число в тексті i18n (`app/lib/i18n/*.ts`), якого немає в `rules.2026.json`.

Питання, яке ставиться до кожної цифри: **звідки вона і хто це звірив.** Якщо
відповідь із памʼяті рев'юера — це вже знахідка.

### P0-2. Текст, що радить дію замість інформування

Правило: [`product-safety.md`](../../rules/product-safety.md).

Ловити в будь-якому user-facing рядку (`app/lib/i18n/*.ts`, літерали в `.tsx`):
- друга особа + імператив про вибір форми («оберіть», «переходьте»,
  «оформіть», «не переплачуйте»);
- порівняльна оцінка вигоди («вам вигідніше», «краще для вас», «оптимально»);
- обіцянка результату («заощадите», «сплатите менше»).

Межа: описати **різницю** можна і треба («чистими виходить більше, але
лікарняний не виплачується»). Не можна назвати переможця за користувача.
Формулювання, яке проходить: назвати наслідок обох варіантів у тому самому
реченні й зупинитись.

### P0-3. Брудний шар `app/lib/calc/`

Правило: карта шарів у [`CLAUDE.md`](../../../CLAUDE.md) §«Правило залежностей».

Ловити:
- будь-який npm-імпорт у `app/lib/calc/**` (нуль залежностей — не побажання,
  а умова: розрахунок мусить рахуватись у голому Node);
- браузерний глобал (`window` / `document` / `navigator` / `localStorage` /
  `sessionStorage`) поза `app/lib/storage.ts`;
- імпорт компонента чи сторінки з `app/lib/**`;
- читання `rules.2026.json` напряму з UI повз `calc/`.

Цей P0 перекривається детермінованим шаром (`npm run test:arch` + 
`architecture.test.ts`) — і це не привід його не перевіряти: рев'ю бачить дифф
раніше, ніж гейт, і називає причину, а не лише факт падіння.

## P1 і P2

- **P1** — логічна помилка, що змінює висновок: межа/`off-by-one` на порозі
  ярусу, порожній стан, переплутаний пріоритет правил. Блокує мердж.
- **P2** — дублювання, читабельність, мертвий код. Не блокує; іде в бэклог або
  окремим комітом.

## Звідки береться дифф

**Робоче дерево, не `origin/HEAD...`.** Вбудований прохід читає лише закомічене,
а `pre-commit-gate` цього репо не дає закомітити червоне дерево — тобто дефект,
який валить тест, до вбудованого рев'ю фізично не доїде. Тому:

```bash
git diff HEAD                 # закомічене + незакомічене на гілці
git status --porcelain        # нові файли, яких diff не показує
git diff master...HEAD        # додатково, якщо гілка вже має коміти
```

Порожній вивід усіх трьох — зупинитись і сказати, що рев'ювати нічого. Не
підмінювати відсутній дифф оглядом усього репо.

## Протокол

1. Зібрати дифф трьома командами вище.
2. Пройти по кожному зміненому файлу тричі — окремо під P0-1, P0-2, P0-3. Не
   змішувати проходи: змішаний прохід дає найгучнішу знахідку і губить решту.
3. Для кожної знахідки: `file:line`, номер P0, **рядок правила репо**, який вона
   порушує, і конкретний фікс.
4. Нуль знахідок — так і сказати. Не добирати P2, щоб звіт не був порожнім.
5. **Записати звіт у файл, не лише в чат** —
   `docs/reviews/<YYYY-MM-DD>-<гілка>.md`. Далі застосування йде **окремим,
   свіжим проходом**, який читає цей файл і дифф, а не памʼять рев'юера:
   той, хто щойно писав знахідку, схильний захищати її формулювання.
6. Не застосовувати фікси в тому ж проході, у якому знайшов. Виняток — фікс на
   один символ, названий у звіті дослівно.

## Чесна межа

LLM-рев'ю **не заміняє** детерміновані ворота і не є їх дублікатом:

| Шар | Що ловить | Чого не ловить |
|---|---|---|
| `npm test` (193) | зсув відомого числа, зламану гілку логіки | нову цифру без джерела; будь-який текст |
| `test:arch` + `architecture.test.ts` | npm-імпорт і браузерний глобал у `calc/` | сенс тексту й походження цифри |
| `check-stale-rules.mjs` | протерміноване `verified_at` у `rules.2026.json` | літерал, зашитий повз `rules.2026.json` |
| цей прохід | усі три P0 за змістом | те, чого немає в діфі |

Жоден із рядків не покриває решту. Рев'ю ставиться **поверх** гейта, перед
`gh pr ready`, а не замість `npm run verify`.
