# Аудит артефактів фічі

Скіл **інспекційний**, не workflow: він не веде фічу вперед і нічого не пише на
диск. Його єдиний вихід — таблиця статусів у чат плюс 3–5 рядків рекомендацій.

Причина існування: артефакти цього репо історично не лежать в одному місці. У
фічі `nierejestrowana` (у проді з 2026-08-03) артефакти сімох фаз розсіяні по
десятьох контейнерах, а теки `docs/features/nierejestrowana/` не існувало взагалі
— вона з'явилась лише під сам аудит
([artifact-inventory.md](../../../docs/features/nierejestrowana/artifact-inventory.md)).
Аудит, який дивиться лише в теку фічі, чесно відзвітує «0 з 9» і збреше.

## Крок 0 — вхід і межа

Аргумент — `<slug>` фічі (`tg-assistant`, `nierejestrowana`, `zlecenie`).

Slug у цьому репо буває **двох видів**, і вони не збігаються:

- slug **теки** — `docs/features/tg-assistant/`;
- slug **коду** — ім'я сценарію (`nierejestrowana.ts`, ключ `nierejestrowana.*`
  у `rules.2026.json`), яке зазвичай коротше за назву гілки
  (`feat/f2-dzialalnosc-nierejestrowana`).

Перед скануванням переконатись, що фіча взагалі має слід:

```bash
ls -d docs/features/<slug> 2>/dev/null
git grep -il '<slug>' -- app docs scripts SPEC.md ARCHITECTURE.md README.md | head -20
```

Обидва порожні → зупинитись і спитати правильний slug. Не вигадувати фічу.

## Дев'ять артефактів і де їх чекати

| # | Артефакт | Очікуваний шлях | Коли обов'язковий |
|---|---|---|---|
| 1 | `idea-brief` | `docs/features/<slug>/idea-brief.md` | завжди (XS — можна пропустити) |
| 2 | `PRD` | `docs/features/<slug>/PRD.md` | S і більше |
| 3 | `sad` | `docs/features/<slug>/sad.md` | M+ |
| 4 | `adr/` | `docs/features/<slug>/adr/NNNN-*.md` | M+ (2–4 для S) |
| 5 | `data-model` | `docs/features/<slug>/data-model.md` | **лише якщо є БД** |
| 6 | `openapi.yaml` | `docs/features/<slug>/contracts/openapi.yaml` | **лише якщо є HTTP-поверхня** |
| 7 | `api-sync-report` | `docs/features/<slug>/contracts/api-sync-report.md` | разом із №6 |
| 8 | `tasks/` | `docs/features/<slug>/tasks/` (`_epic.md`, `tracker.md`, `S-*.md`) | S і більше |
| 9 | `CONTEXT` | `docs/features/<slug>/CONTEXT.md` | завжди |

Розмір фічі береться з рубрики в `CLAUDE.md` (XS / S / M+), а не вгадується. Якщо
в `idea-brief.md` є `feature_size` у frontmatter — брати звідти; немає — спитати
одним питанням, не припускати.

### Три артефакти, які тут н/д — і умова, за якої вони перестають бути н/д

Проєкт клієнтський і детермінований: розрахунок іде в браузері, БД і HTTP API
немає (DECISIONS). Артефакти 5–7 тому структурно незастосовні. Позначати їх
«відсутніми» — означає щоразу генерувати три фальшиві пропуски, після чого звіт
перестають читати цілком.

Умова знімається **машинно**, не на око:

```bash
test -d app/api && echo "HTTP-поверхня з'явилась → №6, №7 більше не н/д"
grep -qE '"(pg|postgres|drizzle-orm|prisma|@neondatabase/serverless)"' package.json \
  && echo "БД з'явилась → №5 більше не н/д"
```

Обидві команди мовчать → у звіті статус `н/д` з причиною. Хоч одна відповіла →
статус рахується як для решти.

## Чотири статуси

| Статус | Критерій |
|---|---|
| `є` | Файл на очікуваному шляху існує **і не порожній**: ≥1 заголовок `##` і ≥20 непорожніх рядків. Файл-заглушка з самим frontmatter — це `нема`, а не `є` |
| `стейл` | Файл існує, але його останній коміт **старший** за останній коміт коду фічі (див. нижче) |
| `нема` | Файла на очікуваному шляху немає. Якщо при цьому знайдено еквівалент в іншому контейнері — це фіксується окремою колонкою, статус лишається `нема` |
| `н/д` | Артефакт незастосовний за поверхнею проєкту (див. вище) або за розміром фічі. Причина називається завжди |

### Стейл рахується по git, не по mtime

```bash
# дата артефакта
git log -1 --format=%aI -- docs/features/<slug>/PRD.md
# дата коду фічі — ЛИШЕ файли-визначники, не всі згадки slug
for f in app/lib/calc/scenarios/<slug>.ts app/lib/rules/rules.2026.json; do
  git log -1 --format=%aI -- "$f"
done | sort | tail -1
```

Брати `git grep -il '<slug>' -- app | xargs …` — спокусливо і **неправильно**:
у вибірку потрапляють `i18n/uk.ts`, `page.module.css` і тести, які змінюються
щоразу, коли хтось переписує текст або верстку. На `nierejestrowana` це давало
дату «сьогодні» від правки формулювання в i18n — і рівно чинний `SPEC.md`
позначався стейлом. Визначники — це те, що змінює **поведінку**: модуль
сценарію і блок правил.

Стейл — **підозра, а не вирок**: він означає «код рухався пізніше, перевір, чи
твердження ще чинне», і в рекомендаціях формулюється саме так.

### Артефакт постфактум — окремий прапорець

Порівнювати лише «новіший/старіший за останній коміт» замало. Артефакт фази 1–2
(AC, PRD, критерій у `SPEC.md`), який з'явився **пізніше за перший коміт коду**,
формально свіжий, а фактично не виконував роботи контракту:

```bash
git log --reverse --format=%aI -- app/lib/calc/scenarios/<slug>.ts | head -1   # код
git log -1 --format=%aI -- <артефакт>                                          # артефакт
```

Артефакт пізніший → у звіті помітка `постфактум` поруч зі статусом. Це не
пропуск і не стейл, а третя річ: опис того, що вже зроблено, замість рамки для
того, що робиться.

**Скрізь `%aI` (author date), ніколи `%cI`.** Гілки в цьому репо вливаються
rebase-ом, і він переставляє committer-дату всім комітам гілки на одну й ту саму:
у F2 всі три коміти мають `%cI = 18:50:54`, тобто по committer-даті порядок
всередині фічі не існує взагалі. `%aI` зберігає справжній: EVIDENCE 18:18:29 →
код 18:19:29 → SPEC 18:20:51.

`mtime` для цього непридатний: у свіжому клоні він дорівнює часу checkout-у для
**всіх** файлів одразу, і аудит покаже «все свіже» на репо, яке ніхто не читав.
Git-дата переживає клон.

Артефакт без жодного коміту (є в робочому дереві, не застейджений) — це не `є` і
не `стейл`, а окремий рядок у рекомендаціях: «написаний, але не закомічений».

## Крок 2 — еквіваленти поза текою фічі

Обов'язковий прохід, без нього звіт неповний. Для кожного `нема` перевірити, чи
роль артефакта не виконує щось інше:

| Артефакт | Ймовірний еквівалент у цьому репо |
|---|---|
| `PRD` §Goals / §AC | рядок критерію в `SPEC.md`; рядок задачі в `docs/BACKLOG.md` |
| `sad` / `adr/` | `ARCHITECTURE.md`, `docs/architecture-map.md`, запис у `docs/DECISIONS.md` |
| `CONTEXT` (глосарій, NOT-межі) | §Сценарій у `docs/EVIDENCE.md` — саме там живуть межі «X, а не найближчий сусід Y» |
| `tasks/` | чекліст «Зараз у роботі» в `docs/STATE.md` |
| рев'ю / приймання | опис PR (`gh pr list --search '<slug>'`), запис про візуальний рев'ю в `STATE.md` |

```bash
git grep -n -i '<slug>' -- SPEC.md docs/EVIDENCE.md docs/DECISIONS.md docs/BACKLOG.md \
  docs/STATE.md docs/PROJECT.md docs/OPEN-RISKS.md docs/JOURNAL.md \
  ARCHITECTURE.md docs/architecture-map.md CAPSTONE_LOG.md
export PATH="$HOME/.local/bin:$PATH"   # gh лежить поза PATH неінтерактивного шелу
gh pr list --state all --search '<slug>' --json number,title,url,headRefName 2>/dev/null
```

Еквівалент **не підвищує** статус до `є`. Він відповідає на інше питання: чи це
пропуск, чи це артефакт не в тому контейнері — а це різні рекомендації.

`docs/JOURNAL.md` у списку не випадково: післямортем помилки, знайденої під час
фічі, — артефакт фази рев'ю, і шукати його більше ніде.

### Кожен збіг перевіряти на омонім

Grep за slug ловить **термін**, а не сутність. На `nierejestrowana` з десяти
контейнерів чотири (`docs/PROJECT.md`, `docs/OPEN-RISKS.md` §4, `docs/DECISIONS.md`
§Оплата, рядок у `docs/BACKLOG.md`) виявились про **інше**: про форму, якою
оплачується сам проєкт, а не про сценарій порівняння. Слово те саме, сутність
різна.

Тому перед звітом кожен збіг ділиться на дві купи — **про фічу** і **омонім** — і
в таблицю йде лише перша. Омоніми називаються окремим рядком під таблицею: вони
не пропуск, вони шум, і наступний аудит наступить на них знову.

Той самий фільтр — до `gh pr list`: пошук повертає й PR, де slug лише згаданий в
описі. Фічевими вважати ті, чий `headRefName` або заголовок містить slug.

## Крок 3 — таблиця статусів

Рівно 9 рядків, у порядку фаз:

```
| # | Артефакт | Статус | Шлях / контейнер | Дата (git) | Еквівалент деінде |
```

Під таблицею — один рядок підсумку: `є N · стейл N · нема N · н/д N`.

### Дев'ятка не покриває всіх фаз — дописати два рядки вручну

Артефакти 1–9 закривають фази 1–4 (PM, BA/PO, Architect, TL) і 8 частково. Фази
**5–7** (код, рев'ю, QA) і **9** (моніторинг) у списку не представлені зовсім, тож
аудит, обмежений дев'яткою, структурно не здатен побачити найдорожчий пропуск —
той, де фіча в проді, а метрики немає.

Тому для фічі, що вже викотилась, до таблиці додаються два рядки:

- **Рев'ю** — `gh pr view <N> --json reviews`; нуль рев'ю на змердженому PR
  називається прямо, а не ховається за наявністю опису.
- **Моніторинг** — чи існує бодай одне джерело даних, яке підтвердить гіпотезу
  фічі. Немає — це рядок №1 у рекомендаціях, незалежно від решти статусів.

## Крок 4 — рекомендації, 3–5 рядків

Не переказ таблиці. Сортування — за тим, **що блокує найближчу наступну фазу**, а
не за номером артефакта. Кожен рядок — одне речення: що бракує → чим це вже
коштує або коштуватиме → найдешевший наступний крок.

Пріоритет, коли пропусків більше п'яти:

1. Артефакт, без якого не стартує наступний скіл ланцюга (`write-prd` без
   `idea-brief`, `break-tasks` без PRD) — це жорсткий гейт, не побажання.
2. `стейл` перед `нема`: застарілий артефакт гірший за відсутній, бо його читають
   і йому вірять.
3. Артефакт, чий еквівалент знайдено в чужому контейнері — тут рекомендація не
   «написати», а «перенести й лишити посилання».
4. Пропуски, дешеві за розміром фічі (XS без SAD), у рекомендації **не йдуть
   узагалі** — вони вже пояснені в колонці `н/д`.

## Чого скіл не робить

- Не створює й не редагує артефактів — навіть порожніх заготовок. Аудит, який
  сам засіває файли, наступного разу відзвітує про власну роботу як про наявність.
- Не судить **якість** змісту: PRD із трьома порожніми секціями — це `є`. Логіку
  дивиться людина або окремий рев'ю-агент.
- Не чіпає `.claude/settings.json` і не запускає `npm test` — інспекція має бути
  дешевою, інакше її не запускають.
